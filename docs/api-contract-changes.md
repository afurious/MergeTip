# API contract changes

Every change to the frozen v1 contract in [`api-contract.md`](api-contract.md), newest first.
Changes are additive: nothing is removed or renamed, and old shapes keep working. The one
exception is the removal of fiat payouts (2026-10-27), which no client had used.

| Date | Change | Why |
| --- | --- | --- |
| 2026-10-27 | **Breaking, deliberate:** fiat payouts removed. Gone: `GET /v1/payouts/countries`, `GET /v1/payouts/countries/{code}`, `GET` and `POST /v1/me/payout-methods`, `PATCH` and `DELETE /v1/me/payout-methods/{id}`, `POST /v1/webhooks/bitnob`, `Tip.fiat`, the `fiat` value of `ReceiveStatus.method` and `ReceiveStatus.fiat_min_sats`, and the `fiat_disabled` error code | Product decision: MergeTip pays receivers over Lightning only (RFC 0004 withdrawn). Nothing was released and no frontend code called these |
| 2026-10-27 | `GET /v1/email/unsubscribe` now only shows a confirm page (opening the link changes nothing); `POST` unsubscribes, answering 204 to an RFC 8058 one-click (`List-Unsubscribe=One-Click`) and an HTML page to the confirm page's button | Mail scanners and link previews fetch every link in an email, and were unsubscribing people (M4 review) |
| 2026-10-27 | `PATCH /v1/me/settings` answers 403 `reauth_required` when a change loosens a protection (turning confirmation codes off, raising the confirmation threshold, the per-tip or the daily cap) unless the request uses the web session cookie from a sign-in in the last 15 minutes. The web app should send the user through `/v1/auth/github/login?redirect=/settings/...` and retry. Tightening needs nothing extra | A stolen session (or extension token) could otherwise switch codes off and confirm a large tip (M4 review) |
| 2026-10-26 | `Tip` gains an optional `fiat` object (`currency`, `amount`, `rate`, `fees` as decimal strings, `status`); `null` for Lightning tips | FR-10.6: the dashboard shows fiat amount, rate, fees and delivery status per tip. No destination details are included |
| 2026-10-26 | `/v1/auth/*`, `/v1/claims/*`, `/v1/confirmations/*/otp` and `/v1/tips/comment` may answer 429 `rate_limited` with `Retry-After` (per IP, and per user when signed in). Request bodies are capped at 64 KiB (5 MiB for GitHub webhooks, 256 KiB for Resend and Bitnob) and answer 413 above it. Every response carries HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `X-Frame-Options: DENY`; credentialed responses add `Cache-Control: no-store` | Abuse protection and HTTP hardening (PRD "Security") |
| 2026-10-26 | Added `POST /v1/webhooks/bitnob` (Bitnob payout events: `x-bitnob-signature` HMAC-SHA512 over the raw body, deduplicated by `event_id`; 200, 401 `invalid_signature`, 400 without an event ID, 404 when unconfigured) | Fiat tips are `paid` only when Bitnob confirms delivery (FR-10.5) |
| 2026-10-26 | Fiat payouts (FR-10, RFC 0004), all additive and all 404 `fiat_disabled` until enabled: `GET /v1/payouts/countries`, `GET /v1/payouts/countries/{code}` (the receive form generated from Bitnob's requirements: `forms[].fields[]` with `key`, `label`, `type`, `required`, `component`, `pattern`, `min_length`, `max_length`, `placeholder`, `options`), `GET`/`POST /v1/me/payout-methods`, `PATCH`/`DELETE /v1/me/payout-methods/{id}`. Errors `account_lookup_failed`, `fiat_unsupported` (422) and `fiat_unavailable` (502). Accounts are only ever returned masked (`****6789`). `receive-status` gains `method: "fiat"` and an optional `fiat_min_sats` | Receivers in NG, GH and KE choose local currency; the extension warns senders below the corridor minimum |
| 2026-10-26 | Error codes for the M4 endpoints: `GET /v1/me/tips` answers 422 `invalid_query` for an unknown `direction` or `state` or a bad cursor; `POST /v1/tips/comment` answers 422 `invalid_tip` (bad repo, receiver, amount or note), 403 `github_forbidden` (GitHub refused the comment), 401 `github_reauth_required` and 502 `github_unavailable`. A note is sent as one line, without backticks or `/tip`. `GET /v1/users/{login}/receive-status` answers `none` for users MergeTip has never seen | The frozen contract lists only the happy paths and `app_not_installed`; the extension needs to tell these cases apart |
| 2026-10-26 | Added `GET` and `POST /v1/email/unsubscribe?token=` (GET answers with an HTML page; POST is RFC 8058 one-click and returns 204; 400 `invalid_token`) and `POST /v1/webhooks/resend` (Svix-signed Resend delivery events; 401 `invalid_signature`, 404 when unconfigured) | One-click unsubscribe in every email (FR-11.5) and delivered/bounced/opened tracking (FR-11.7). Neither is called by the web app |
| 2026-10-26 | Confirmation error codes added: `not_awaiting_confirmation` (409, tip already confirmed, cancelled or expired), `otp_not_enabled` (422, codes are off), `otp_unavailable` (422, no email on file or email not configured), `otp_rate_limited` (429, one code a minute), `email_failed` (502). `POST /v1/confirmations/{tip_id}` accepts an empty body when codes are off | The frozen contract names only the happy path, `confirmation_expired` and `otp_invalid`; clients need to tell the other outcomes apart |
| 2026-10-26 | Frontend heads-up, no API change: claim links are `${PUBLIC_BASE_URL}/claim/{token}`, so the web route must be `/claim/[token]` (the scaffold has `claim/[tipId]`). `GET`/`POST /v1/claims/{token}` take that token, not a tip ID | Claim links carry an unguessable single-use token (FR-11.6); a tip ID would let anyone enumerate pledges |
| 2026-10-26 | `POST /v1/claims/{token}` accepts an empty body (no `Content-Type`) as well as `{ lightning_address? }` | "Claim with my saved address" needs no body |
| 2026-10-24 | GitHub App manifests: the OAuth callback is `${API_PUBLIC_URL}/v1/auth/github/callback` (was the web app's `/auth/github/callback`), and the App requests `email_addresses: read` | The API exchanges the code and sets the session cookie, as the contract's `/auth/github/callback` route says; the email permission provides the verified email for pledge notices (FR-11.2). Infrastructure only: no API shape changes |
| 2026-10-24 | `GET /healthz` documented in OpenAPI alongside `GET /v1/health` | Fly health checks already use `/healthz`; `/v1/health` is the contract endpoint for clients |
