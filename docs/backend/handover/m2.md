# M2 handover: GitHub App core

Branch `backend/m2-github-app`, branched from `dev` at `8f08b3a` (M1 merged). Not pushed or
merged.

## What works

A signed `/tip` comment becomes a verified tip and the right bot reply. Payment is stubbed.

- **Parser** (`mergetip-parser`). Implements the full grammar. Ignores code, quotes and HTML
  comments. Every error carries the command's text and index, plus a fix-it help line. User input
  is quoted safely in messages. Covered by table tests, snapshots, and 2,000-case property tests
  (never panics, deterministic, accepted commands obey the grammar).
- **Webhook endpoint** (`POST /v1/webhooks/github`). Checks the HMAC over the raw body, stores the
  delivery and enqueues `process_event` in one transaction, then returns `202`. Duplicate delivery
  IDs are acknowledged and ignored. Errors: `invalid_signature` (401), `missing_header` and
  `invalid_payload` (400).
- **GitHub client** (`OctocrabGitHub`). App JWT with per-installation token caching, bounded
  pagination (10 × 100), and rate limits mapped to `RateLimited { reset_at }`. octocrab's own
  retries are off; the job queue retries instead, at GitHub's reset time for rate limits. Logins
  and repository names are validated before they go into API paths.
- **Verifier.** Every PRD rule: identity (exists, not the sender, not a bot, account at least 30
  days old), then PR author, submitted review (not for `on-merge`), commit author, co-author
  trailer (public email or either noreply form), and issue author/commenter/linked PR. GitHub
  failures are always errors, never rejections.
- **Engine** (new `mergetip-engine` crate):
  - routes events (comments, installation lifecycle, repository adds and removes);
  - creates tips idempotently and applies the limits (5 per comment, 20 per hour, 3 per pair per
    thread, `on-merge` only on PRs);
  - moves a tip to `awaiting_sender` (24 h) when the sender has no wallet;
  - after verification, decides: over the per-tip cap → rejected; over the threshold →
    `awaiting_confirmation` (1 h); `on-merge` → `held`; otherwise `paying`.

  Every state change commits together with its follow-up jobs.
- **Replies.** Rendered when the job runs, from current data. Messages someone must act on (parse
  errors, connect wallet, confirm, rejections) are new comments, so the mention notifies. Status
  updates (held, paid) are appended to one collapsed status comment per thread, serialised with an
  advisory lock. If someone deletes that comment, a new one is started. Reactions are 👀 → 🚀/😕.
  Duplicate replies are prevented with dedupe keys. Notes are escaped, so a note can't ping anyone
  or inject Markdown.
- **Stub payer.** `STUB_PAYER=true` marks `paying` tips `paid` with a random but consistent
  hash/preimage and posts the receipt. Config refuses it in production. Without it, `pay_tip` has
  no handler, so tips wait in `paying` for the M3 payer.
- **E2E** (`mergetip-e2e`). The real api router and worker `Runner`, Postgres, and the octocrab
  client against a wiremock GitHub. Covers: review → `/tip` → paid with receipt and reactions;
  four deliveries of one comment → one tip; a forged signature → nothing happens.
- **`make dev-app`.** The GitHub App manifest flow on localhost. Writes `.secrets/github-app.pem`
  (0600) and the App's keys into `.env` without touching other lines. A wrong `state` is refused.

## How to run and demo

```sh
make check-backend                 # 177 tests
# Live, with your own dev App:
#   1. create https://smee.io/new, put it in .env as SMEE_URL
#   2. make dev-app, then install the App on a test repo
#   3. set STUB_PAYER=true and PUBLIC_BASE_URL in .env
#   4. make smee, make dev-api, make dev-worker
#   5. review a PR, then comment `/tip @reviewer 100`
```

## Not verified here

- **The live exit criterion.** `/tip` on a real repo through a real dev App, with 👀 → receipt →
  🚀 in under 5 s, needs your GitHub account and an App. It is covered offline by the E2E test,
  which completes in under 1 s, but has not been run against github.com. Run step 5 above once
  `make dev-app` is done.
- **Coverage (`cargo llvm-cov`)** is not installed. The parser and verifier have tests for every
  rule and error path, but the 90% figure has not been measured.

## Deviations and decisions

- **`.github/mergetip.yml` is not fetched yet.** The prompt asked for it on installation events,
  but the file is per repository and the schema stores config per installation. It only matters
  for P2 auto-tip rules (FR-9.1), which will need per-repo storage then. `get_repo_file` was left
  out of the trait for the same reason.
- **Closing-PR rule on issues** is implemented as "a PR authored by the receiver cross-referenced
  this issue" (timeline `cross-referenced` from a pull request). GitHub's timeline doesn't cleanly
  mark which cross-references close the issue.
- **Decision order** checks the threshold before `on-merge`, so a large on-merge tip is confirmed
  first and then waits for the merge (`awaiting_confirmation → held`, as the state machine
  allows).
- **`transition` takes a `TipPatch`.** Columns such as the receiver, verification evidence, error
  code, expiries and payment proof are set in the same UPDATE as the state change, and never
  erased.
- **Verifier tests** use the `FakeGitHub` test double (`mergetip-github` `testing` feature).
  Request and response mapping is tested separately against wiremock.
- **New migrations:** `bot_comment_lines` (status lines stored so appends don't re-read GitHub).

## Repository and config changes

- **New crates:** `engine`, `e2e` (dev-only), `devtools/dev-app`.
- **Env vars:**
  - The api now requires `GITHUB_WEBHOOK_SECRET`.
  - The worker now requires `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY_PATH` and
    `PUBLIC_BASE_URL`, and takes optional `STUB_PAYER` and `GITHUB_API_URL`.
  - `GITHUB_APP_SLUG` is documented in `.env.example`.
- **`Makefile`:** `dev-app` is implemented, and `SMEE_URL` is exported from `.env`.
- **`.gitignore`:** now covers `.secrets/`.
- **OpenAPI:** documents the webhook route. The frontend `schema.d.ts` was regenerated, and
  `pnpm check` passes. No contract changes: the route was already in the contract.

## Known risks and follow-ups for M3

- **No real payments yet.** M3 replaces `pay_tip_stub` with the LNURL + NWC payer and adds
  `payment_attempts`.
- **No resume or expiry yet.** `awaiting_sender` tips get a 24 h `expires_at` but nothing resumes
  or expires them until M4 (wallet connect resume, expiry worker).
- **Confirm links point at an endpoint that doesn't exist yet.** `awaiting_confirmation` links go
  to `/confirm/{tip_id}`, which arrives in M4.
- **The dev manifest's OAuth `callback_urls` still points at the web app.** M3 fixes this when it
  adds OAuth.
- **`pull_request.closed` is acknowledged but not acted on.** M4 resolves `held` tips there.
- **A reply can be posted twice in a rare crash window.** If the worker dies after GitHub accepted
  a reply but before the job completed, the reply is posted again on retry. Dedupe keys stop
  duplicate enqueues, not this window.
