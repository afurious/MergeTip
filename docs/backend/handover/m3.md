# M3 handover: Auth, wallet connect and real payments

Branch `backend/m3-payments`, branched from `dev` at `d971c92` (M2 merged). `main` is still the
scaffold (`04755b9`), so this branch carries M1 and M2 too. Not pushed or merged.

This is the demo MVP: a `/tip` comment moves sats from the sender's own NWC wallet to the
receiver's Lightning address, and the bot posts a receipt with the payment hash.

## What works

- **Schema.** `sessions` and `payment_attempts`. Two partial unique indexes enforce the
  money-safety rules: one open (`pending`/`unknown`) attempt per tip, and one `succeeded` attempt
  per tip. The second index is the double-pay guard, and it is enforced by the database itself.
- **GitHub OAuth** (`/v1/auth/github/login`, `/callback`). The `redirect` parameter must be a
  same-origin path; anything else becomes `/dashboard`. The state cookie is compared in constant
  time. Access and refresh tokens and the primary verified email are envelope-encrypted. Web
  sessions last 30 days and slide. The manifests now send OAuth callbacks to the API and request
  `email_addresses: read`.
- **Sessions.** `AuthUser` (cookie or bearer) and `SessionUser` (cookie only). The CSRF rule:
  cookie-authenticated writes need an allowed `Origin`, and a JSON `Content-Type` when they have a
  body. Endpoints: `POST /auth/logout`, `POST /auth/extension-token` (a 7-day bearer) and
  `GET /me`. A helper refreshes the GitHub user token before any call made as the user.
- **LNURL** (`payer::LnurlClient`, hand-rolled `reqwest`; RFC 0002 explains why not `lnurl-rs`).
  Implements LUD-16 resolution, `min/maxSendable`, comment trimming and `{status:"ERROR"}`.
  Before an invoice is used, it is checked for the exact amount, at least 120 s left before expiry,
  the configured network, a valid signature and the description hash. Each failure is a distinct
  `ResolveError`, and none reaches the wallet. `http` is allowed only for local hosts in dev.
- **NWC** (`payer::NwcWallet`, on the `nwc` 0.45 crate). Uses NIP-44 when the wallet's info event
  offers it, otherwise NIP-04. Wallet error codes are mapped and split into retryable and terminal.
  A timeout is `PayError::Timeout`, meaning the outcome is unknown, and is never treated as a
  failure.
- **Wallet, address and settings** (`PUT/DELETE /me/wallet`, `PUT /me/lightning-address`,
  `PATCH /me/settings`). The URI is checked with `get_info` and must offer `pay_invoice`. It is
  sealed with AAD `wallet_connections.nwc_uri:{id}`, and the previous connection is revoked in the
  same transaction. The URI is never echoed or logged; a log-capture test asserts this.
  `spent_today_sats` is the sum of pending, unknown and succeeded attempts since UTC midnight.
- **`pay_tip`** (engine). Order of work:
  1. Check the `payments_enabled` kill switch.
  2. Resolve and validate the invoice, outside any transaction.
  3. Reserve the payment in one transaction: lock the tip and the sender row, re-check the
     per-tip and daily caps, insert a `pending` attempt and set the tip's `payment_hash`.
  4. Decrypt the NWC URI (the worker is the only place this happens) and pay, with a 60 s timeout.

  Outcomes:
  - Success: the preimage is checked against the payment hash, the tip moves to `paid`, and the
    receipt and 🚀 reaction are queued.
  - Terminal error: the tip moves to `failed` with a mapped message.
  - Retryable error: up to 3 attempts.
  - Timeout: the attempt becomes `unknown` and `reconcile_payment` is queued.
  - Receiver with no address: the tip becomes a pledge, without a claim link until M4.
- **Reconciliation.** Calls `lookup_invoice` if the wallet advertises it. Settled with a valid
  preimage → paid. Failed → retry if the budget allows. Pending or unsupported → re-check at
  `min(now + 30 s × 2^n, invoice expiry + 60 s)`. After expiry with no settlement, the attempt
  fails and a fresh attempt with a new invoice is allowed. A pay job that finds an open attempt
  (a worker crashed mid-payment) reconciles instead of paying again.
- **Devtools mocks.**
  - `mock-lnurl` serves LUD-16 for any `user@localhost:8090`, returning real signed regtest
    invoices with `preimage = HMAC-SHA256(MOCK_SEED, payment_secret)`. Magic users: `wrongamount`,
    `expired`, `badhash`, `down`.
  - `mock-nwc` publishes a NIP-47 info event offering NIP-44, pays those invoices and prints its
    connection URI. Magic amounts: 666 insufficient balance, 777 pays but the answer is lost,
    888 quota exceeded, 999 never answers.
  - Both are wired into `docker-compose.yml` with a shared `MOCK_SEED`. Their tests reuse the
    payer's invoice validation.
- **E2E** (`mergetip-e2e`, all real except the outside world). Journey A:
  1. Both users sign in through OAuth.
  2. The maintainer connects the mock wallet through `PUT /me/wallet`, on an in-process relay,
     and sets caps.
  3. The reviewer links an address.
  4. A signed `/tip` arrives and is verified, then paid over NWC with a checked preimage.
  5. The receipt is posted, and `spent_today_sats` updates.

  The suite also covers:
  - Three redeliveries plus a second delivery → one payment.
  - A wrong-amount LNURL invoice → nothing reserved or paid.
  - A worker killed mid-`pay_invoice` (handler aborted, lease expires, a second worker takes
    over) → reconciled to paid, one succeeded attempt, wallet paid once.
  - A forged signature → nothing happens.

## How to run and demo

```sh
docker compose up -d          # postgres, relay, mailpit, mock-nwc, mock-lnurl
make check-backend            # fmt, clippy, all tests incl. e2e, sqlx offline check
docker compose logs mock-nwc  # copy the nostr+walletconnect:// URI it prints

# Live, with your dev App (see m2.md for make dev-app / make smee). Leave STUB_PAYER unset.
#   1. make dev-api, make dev-worker, sign in at the web app
#   2. Settings → wallet: paste the mock-nwc URI
#   3. As the receiver: set the Lightning address to <anything>@localhost:8090
#   4. Comment `/tip @receiver 2100 for the review` on a PR they reviewed
```

The relay test against the compose relay is opt-in:
`LIVE_RELAY_URL=ws://localhost:7000 cargo test -p mergetip-payer -- --ignored live_relay`.

  and a staging deploy, so it is recorded in `BLOCKERS.md` and not faked.
- The offline journey with the dev GitHub App was not run in this session, because it needs a
  personal App and smee. The same path is covered in-process by the e2e suite, and the compose
  mocks were started and checked: the LNURL endpoints answer, and the wallet connects to the
  relay and prints its URI.

`API_PUBLIC_URL`, `EXTENSION_ORIGINS`, `GITHUB_OAUTH_URL` (optional, for a mock or GHES),

The compose-only `PUBLIC_RELAY_URL` sets the relay written into the mock wallet's URI.

## Known risks

- **Plaintext URI copy.** After decryption, `pay_tip` copies the NWC URI into a plain `String` for
  the `nwc` client, so that copy is not zeroised on drop. It lives only for the payment call. A
  fix needs the connector to accept `Redacted<String>`.
- **Unknown outcomes.** A wallet without `lookup_invoice` leaves an `unknown` attempt waiting
  until its invoice expires (typically 10 min) before a fresh attempt. This is slow but safe.
- **Relay quality.** Public relays vary. Only the in-process relay and `nostr-rs-relay` are
  tested.
- **Mock wallet logging.** `mock-nwc` logs its own connection URI on purpose. It holds no funds,
  but don't run it with keys reused anywhere real.
