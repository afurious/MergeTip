# M4 handover: Edge flows, pledges, confirmations and notifications

Branch `backend/m4-edge-flows`, branched from `dev` at `27f57c1` (M3 merged). `main` is still
the scaffold. Not pushed or merged.

Design: [RFC 0003](../../rfcs/0003-pledges-confirmations-notifications.md).

## What works

- **On-merge holds.** `pull_request.closed` queues `resolve_held`. That job asks GitHub for the
  PR's real state, because the payload is only a hint.
  - **Merged:** each held tip is verified again with the on-merge rules, then moves to `paying`.
    A tip that fails verification is cancelled with the verifier's code.
  - **Closed unmerged:** every held tip is cancelled with "PR closed without merge".
  - Redeliveries do nothing.
- **Awaiting sender.** `PUT /me/wallet` queues `resume_sender_tips` in the transaction that
  stores the wallet. Unexpired tips move on to verification; expired ones are cancelled.
- **Pledges and claims.** When the receiver has no address, the tip becomes a pledge for 30 days.
  - The claim token is stored hashed, plus a sealed copy for later emails (RFC 0003 explains why).
  - The reply carries `${PUBLIC_BASE_URL}/claim/{token}`.
  - `GET /v1/claims/{token}` is public.
  - `POST /v1/claims/{token}` requires the receiver's web session. It is single use: the token is
    cleared on claim. Error codes: 409 concurrent, 410 expired, 422 `no_address`.
  - Signing in links the user to the receiver row by GitHub ID.
- **High-value confirmation.** The `/v1/confirmations/{tip_id}` endpoints require the sender's
  web session; the extension's bearer token is refused.
  - Optional email OTP: an HMAC under an HKDF subkey, valid 10 min, one new code per minute, five
    attempts before the code is thrown away.
  - A confirmed tip goes to `paying` (`now`) or `held` (`on-merge`). A held tip is checked
    against GitHub at once, so a PR that already merged pays straight away.
  - A test shows comments (`/confirm`, a replayed `/tip`) can't release a tip.
- **`notify` crate.**
  - `Mailer` trait with two providers: `ResendMailer` (idempotency key, 10 s timeout) and
    `SmtpMailer` (plain SMTP via lettre, dev/Mailpit only; refused outside dev).
  - askama HTML and text templates for pledge, reminder, expiry, digest and OTP emails.
  - Every email carries `List-Unsubscribe` and `List-Unsubscribe-Post`.
- **Pledge emails.**
  - Source chain: verified email, then public profile email, then the receiver's commit email on
    the PR (when `email_from_commits` allows it). `noreply` addresses are skipped. Addresses are
    stored encrypted with their source.
  - Digests use the dedupe key `digest:{user}:{day}`, with `run_at` at least 24 h after the last
    email: at most one email a day, and three pledges become one email.
  - The reminder goes out on day 23, and a final notice on expiry.
  - Opted-out users get no email.
  - Signed one-click unsubscribe: `GET`/`POST /v1/email/unsubscribe`.
  - `POST /v1/webhooks/resend` verifies the Svix signature (Svix's documented vector passes) and
    moves `email_status` forward only.
- **Expiry worker.** One recurring `expire_tips` job (dedupe `expire_tips`, every 60 s, seeded at
  worker startup). It closes the 24 h, 1 h and 30-day windows with `SKIP LOCKED` batches of 500,
  and also queues reminders. A test with two concurrent runs over 60 expired tips shows each tip
  moves exactly once.
- **Remaining endpoints.**
  - `GET /v1/me/tips`: keyset cursor, 50 per page, stable while new tips arrive (tested).
  - `GET /v1/users/{login}/receive-status`.
  - `POST /v1/tips/comment`: checks the App is installed and posts as the user with their
    refreshed token. The note is sanitised, and the built line must parse back to exactly the
    requested tip.
  - `DELETE /v1/me`: revokes wallets, deletes sessions, erases tokens, email and address,
    anonymises the login, and closes waiting outgoing tips. Tip rows are kept. Signing in again
    reactivates the account.
- **E2E.** Journeys A, B and C (paid and expired), on-merge, pledge claim, and confirmation with
  OTP → paid, all with the real api and worker against the mock wallet and LNURL.

## How to run and demo

```sh
docker compose up -d
make check-backend
# Templates in a real inbox (Mailpit on :1025/:8025):
LIVE_SMTP_URL=smtp://localhost:1025 cargo test -p mergetip-notify -- --ignored live_smtp
```

## Checked manually

- **Mailpit:** all five templates were sent over SMTP and arrived with HTML and text parts,
  `List-Unsubscribe` and `List-Unsubscribe-Post`. On this machine another project's container
  already held port 1025, so Mailpit ran on spare ports (`docker run -p 11025:1025 -p
  18025:8025 axllent/mailpit`).
- **Not done (staging):** inbox placement in Gmail and Outlook. This needs Resend with SPF, DKIM
  and DMARC on the sending domain.

## Stubbed or mocked

- Real email goes only through Resend; plain SMTP is dev-only. With neither configured, notices
  fall back to GitHub mentions and tips record `email_status = none`.
- The Breez "create a wallet" claim path is frontend work (P4); the API takes any Lightning
  address.

## Contract changes

All are logged in `docs/api-contract-changes.md`, and OpenAPI and `schema.d.ts` are regenerated.

- New endpoints: `GET`/`POST /v1/email/unsubscribe` and `POST /v1/webhooks/resend`.
- New error codes: `not_awaiting_confirmation`, `otp_not_enabled`, `otp_unavailable`,
  `otp_rate_limited`, `email_failed`, `invalid_query`, `invalid_tip`, `github_forbidden` and
  `github_unavailable`.
- Optional bodies on the claim and confirm POSTs.
- **Frontend heads-up:** the claim route must be `/claim/[token]`.

## New env vars

- `RESEND_WEBHOOK_SECRET` (api, optional).
- `API_PUBLIC_URL` is now **required by the worker** too, for unsubscribe links. Set it as a Fly
  secret for `mergetip-worker-staging`.
- `RESEND_API_KEY`, `SMTP_URL` and `EMAIL_FROM` are now read by both api and worker.
- Feature flag row `email_from_commits` (optional). With no row: on outside production, off in
  production.

## Other changes worth knowing

- `deny.toml` now allows CC0-1.0, MITNFA and 0BSD. `cargo deny` was already failing on `dev` for
  the CC0 rust-bitcoin crates from M3; lettre adds 0BSD. All three are permissive. Revert if
  legal disagrees.
- `backend/target` had grown to 131 GB and filled the disk mid-milestone. It was cleaned with
  `cargo clean`. Consider `CARGO_INCREMENTAL=0` for the `check-backend` target.

## Known risks

- Whoever holds a web session can turn OTP off in settings. Re-authenticating before changing
  security settings is a follow-up.
- An unsubscribe link scanner that prefetches GET would opt the user out. The cost is low: GitHub
  mentions continue.
- The commit-email privacy question is still open (PRD); it is governed by the flag.
- The M3 code-review findings on reconciliation are **not fixed**. Three can pay a tip twice:
  - a lookup-less expiry starts a fresh attempt;
  - the lookup asks the current wallet, not the one that paid;
  - the suspension check comes before reconciliation.

  Fix these before real money (see the M3 review notes).
