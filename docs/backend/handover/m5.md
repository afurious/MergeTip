# M5 handover: fiat payouts and production hardening (final)

Branch `backend/m5-fiat-hardening`, branched from `dev` at `b620367` (M4 merged). `main` is still
the scaffold. Not pushed or merged, and no deploy was triggered.

## What works

### Part A: fiat payouts (RFC 0004, behind `FIAT_PAYOUTS_ENABLED` and the `fiat_payouts` flag)

- **Schema:** `payout_methods` (beneficiary envelope-encrypted, one default per user), fiat
  columns on `tips` (`NUMERIC` ↔ `rust_decimal`), `bitnob_events` for webhook dedupe.
- **`fiat` crate:** `BitnobClient` implements `FiatProvider`.
  - Request signing is a pure function, checked against vectors computed independently with
    Python `hmac`.
  - Covers every payouts endpoint the docs name, with retries on 5xx/network only.
  - Errors are typed: `Unavailable`, `Rejected`, `QuoteExpired`, `Decode`.
  - Assumptions are marked `// ASSUMPTION(bitnob)`.
- **Receiver API:** countries; a receive form generated from Bitnob's requirements; add (after
  Account Lookup), list, make default, and delete payout methods.
  - Accounts are only ever shown masked, and a test checks they never reach the logs.
  - `receive-status` gains `fiat` plus `fiat_min_sats`.
  - `Tip` gains `fiat` (amount, rate, fees, status).
- **Pay path:**
  1. Check the corridor limits. Below the minimum, fall back to the Lightning address, or pledge.
  2. Quote with `reference = tip_id`.
  3. Initialize with a unique reference and the callback URL.
  4. Validate the invoice: exact amount, network, signature, ≥ 120 s left.
  5. Reserve the cap and pay over NWC, reusing the M3 safeguards.

  An expired quote gets one re-quote, then `fiat_quote_expired`. A successful payment goes to
  `fiat_processing`; the tip becomes `paid` only on `payouts.withdrawal.success`, with a receipt
  that never shows the fiat amount or destination.
- **Webhooks:** `POST /v1/webhooks/bitnob` checks the HMAC-SHA512 signature, dedupes by
  `event_id` and queues the event. Processing ranks statuses so late or reordered events never
  move a tip backwards. A success that beats the wallet's answer is applied once the payment
  lands. Expired or failed payouts move to `fiat_stuck`.
- **Stuck payouts:** `/app ops fiat-retry` and `/app ops fiat-refund` record the operator in
  `tip_events.detail`. The `FiatPayoutStuck` alert and the `fiat-stuck.md` runbook cover them.
- NG bank, GH mobile money and KE M-Pesa payouts each reach `paid` through the webhook, in
  `engine/tests/fiat.rs::each_corridor_reaches_paid_through_the_webhook`. They run against
  **recorded fixtures**: no sandbox access yet.

### Part B: hardening

- **Metrics** (`METRICS_ADDR`, internal):
  - `tips_final_total{state}`, `tip_e2e_seconds`, `webhook_ack_seconds`,
    `payment_attempts_per_tip`, `nwc_errors_total{code}` and `emails_total{status}`;
  - `github_ratelimit_remaining` and `_limit`, read from every GitHub response;
  - sampled gauges `jobs_ready`, `jobs_oldest_age_seconds`, `jobs_dead`,
    `tips_in_state{state}` and `tips_settled_more_than_once`.

  Nine alert rules are in `deploy/observability/alerts.yml`, validated with `promtool`, one per
  row of the plan's table. Each names its runbook. Sentry is optional (`SENTRY_DSN`), with
  default PII off.
- **Abuse protection:** per-IP and per-user rate limits on auth, claims, OTP and tip comments
  (429 `rate_limited` with `Retry-After`). Security headers (HSTS, nosniff, `no-referrer`,
  `DENY`), and `no-store` on credentialed responses. Body caps per route.
- **Critical tests:** all ten are named in [`critical-tests.md`](../critical-tests.md). That
  includes the new full log scan, `e2e/tests/log_scan.rs`, which runs four journeys at `debug`
  and checks that no secret appears in the logs.
- **Coverage gate:** `make coverage` and a CI job enforce line coverage measured with the whole
  workspace's tests: parser 99.7%, core 91.9%, payer 92.0% (each needs 90%), github 94.3% (needs
  70%).
- **Container:** `cargo-chef` caching, `--locked`, distroless `nonroot`, and OCI labels for
  version and git SHA. Images for every `BIN` were built and run locally as `nonroot:nonroot`
  (api and worker about 19 MB). `migrate` (the entrypoint's argument) serves as the Fly
  `release_command`.
  `deploy/fly/{api,worker}.production.toml` define two machines each in `jnb` and `fra`, with
  health checks and internal metrics.
- **CI:**
  - unit and E2E tests as separate steps;
  - the `sqlx prepare --check` after migrations;
  - OpenAPI drift, comparing the generated document with the committed one;
  - `cargo audit` and `cargo deny` (advisories, licenses, bans, sources);
  - the coverage job.

  `deploy-staging.yml` runs after CI succeeds on `main`: deploy (migrations first), then a
  `/v1/health` smoke test. `deploy-production.yml` runs on `v*` tags, but only if that commit
  passed CI, and behind the `production` environment's approval. Both build from `backend/`
  explicitly. All workflows pass `actionlint`.
- **Runbooks:** payments failing, relay outage, GitHub outage, Bitnob outage, fiat stuck, key
  rotation (with the new `/app ops rewrap`, tested end to end), restore from backup, and disable
  payments (SEV1). The backend README covers the architecture, every env var and the operations
  entry points.

## Open blockers (`BLOCKERS.md`)

- **Bitnob:** a business account, KYB and sandbox credentials. Six documented-but-unconfirmed
  details are marked `ASSUMPTION(bitnob)` in `crates/fiat`. The most important is how a payout
  is funded over Lightning. Fiat stays off everywhere until a sandbox run confirms them.
- **Mainnet smoke test:** one 21-sat payment between two team wallets on staging.
- **Inbox placement:** Gmail and Outlook, after SPF, DKIM and DMARC on the sending domain.
- **Penetration test:** not started; needs a staging environment and an external tester.

| Risk | Impact | Mitigation now | Next step |
| --- | --- | --- | --- |
| M3 review: reconciliation can start a fresh payment when the wallet never confirmed (lookup unavailable, or the wrong wallet asked) | A tip paid twice | The one-success-per-tip index protects our records, not the wallet; `tips_settled_more_than_once` alert | **Fix before real money:** require the original wallet's `lookup_invoice`; otherwise fail for manual review |
| M3 review: suspension check before reconciliation; some error paths strand tips in `paying`; pausing payments fails tips | Stuck or double-handled tips | `JobQueueStalled` alert, runbooks | Fix with the item above |

## Review fixes before commit

A `/code-review` of the uncommitted hardening work found these, and all were fixed before
committing:

- `release_command` took the binary path twice (the image's entrypoint is already `/app`).
- `ops` commands bound the worker's metrics port, so they failed next to a live worker.
- The key rotation could leave api and worker on different keys; it now uses a two-step swap.
- The runbook didn't warn that removing the old key breaks old unsubscribe links.
- Deploys didn't wait for CI.
- The deploy build context was implicit.
- `rewrap` trusted the 1-byte key ID instead of opening the value.
- `migrate` mislabelled its environment.
